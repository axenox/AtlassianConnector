# AI tools

This app ships AI tool prototypes (for use with `axenox/genai` agents) that
let an LLM write to Jira through a configured connection. See
[Jira meta objects](../Metaobjects/index.md) for the read side.

## Table of contents

- [CommentOnJiraTicketTool](#commentonjiratickettool)
- [UpdateJiraDescriptionSectionTool](#updatejiradescriptionsectiontool)

Both tools require an HTTP connection using
`\axenox\AtlassianConnector\DataConnectors\Authentication\AtlassianClientCredentials`
(see [connecting via service account](../Data_connections/Connecting_via_service_account.md))
and restrict which tickets they may act on via an allow-list - neither tool
allows unrestricted writes by default.

## CommentOnJiraTicketTool

`\axenox\AtlassianConnector\AI\Tools\CommentOnJiraTicketTool` adds a plain
text comment to a Jira ticket.

| Property               | Required | Description                                                        |
|-------------------------|:--------:|----------------------------------------------------------------------|
| `connection_alias`      | yes      | The Jira data connection to comment through.                        |
| `allowed_key_prefixes`  | no*      | Only allow commenting on tickets whose key starts with one of these project prefixes (e.g. `["ABC-", "DEF-"]`). |
| `allowed_key_pattern`   | no*      | Alternative/addition to `allowed_key_prefixes`: a regular expression the ticket key must match. |

\* At least one of `allowed_key_prefixes` or `allowed_key_pattern` should be
set. Neither is enforced as required by the class itself, but without one an
unrestricted tool can comment on any ticket visible to the connection's Jira
identity - the tool fails closed only once an allow-list is configured.

```json
{
  "tools": {
    "comment_on_jira_ticket": {
      "alias": "axenox.AtlassianConnector.CommentOnJiraTicketTool",
      "description": "Adds a comment to a Jira ticket.",
      "connection_alias": "your.App.JiraConnection",
      "allowed_key_prefixes": ["ABC-", "DEF-"]
    }
  }
}
```

## UpdateJiraDescriptionSectionTool

`\axenox\AtlassianConnector\AI\Tools\UpdateJiraDescriptionSectionTool`
replaces one managed section of a Jira issue's description without touching
the rest of the document. The model supplies only `key` and Markdown
`content`; the section heading is fixed in the tool configuration.

The tool reads the current raw ADF (Atlassian Document Format) description
through `axenox.AtlassianConnector.JIRA_ISSUE` immediately before every
write, so it does not rely on potentially stale content read earlier by
another agent tool call (e.g. `DataSheetReadTool` against the calculated
`description_markdown` attribute).

| Property               | Required | Default                                                              |
|-------------------------|:--------:|-------------------------------------------------------------------------|
| `connection_alias`      | yes      | -                                                                        |
| `section_heading`       | yes      | Exact top-level heading whose content this tool manages.                |
| `ai_generated_hint`     | no       | `This content was generated by AI and may contain errors. Verify it before use.` |
| `max_content_length`    | no       | `20000`                                                                  |
| `allowed_key_prefixes`  | no       | Only allow tickets whose key starts with one of these prefixes.         |

```json
{
  "tools": {
    "UpdateAgentAnalysis": {
      "alias": "axenox.AtlassianConnector.UpdateJiraDescriptionSectionTool",
      "description": "Replaces the managed Agent Analysis section in a Jira ticket.",
      "connection_alias": "your.App.JiraConnection",
      "section_heading": "Agent Analysis",
      "ai_generated_hint": "This plan was generated by AI and may contain errors. Verify it before implementation.",
      "max_content_length": 20000,
      "allowed_key_prefixes": ["ABC-"]
    }
  }
}
```

### Markdown to ADF conversion

The converter supports paragraphs, headings, bullet and ordered lists,
checklists, GitHub-style tables, blockquotes, rules, fenced code blocks,
links, bold, italic, strikethrough, and inline code. Unsupported constructs
remain visible as plain text rather than being dropped or interpreted as
HTML. Checklists are stored as regular Jira bullet items prefixed with
`[x]` or `[ ]` for broad ADF compatibility.

Markdown headings are shifted below the managed section's actual heading
level. This preserves their relative hierarchy while preventing generated
content from escaping the managed section. If the resulting level would
exceed Jira's H6 limit, that heading remains plain text.

Every managed section starts with a Jira warning panel identifying its
content as AI-generated. The `ai_generated_hint` property customizes this
text; it is rejected if left empty, so the warning cannot be disabled
accidentally. The tool creates the panel itself - the model should not
include a duplicate disclaimer in `content`.

### Section matching rules

The tool searches top-level ADF headings for an exact text match. For an
existing section, it derives the boundary from that heading's actual level
and replaces nodes up to the next heading of the same or a higher level. If
the section does not exist, it is appended as a level-two heading. Duplicate
target headings at any level, malformed ADF, missing tickets, unrestricted
ticket keys, and oversized content cause the operation to fail without
writing.

Jira updates the entire `description` field and does not provide a section
patch operation. Consequently, a human edit made between the tool's read and
its `PUT` can still be overwritten. A dedicated Jira custom field is
required for strict concurrency isolation; this tool only provides
structural isolation within the document being read and written.

## Suggested rollout order

1. Connection works (`TestJiraConnection` succeeds - see
   [Testing REST APIs](../Data_connections/Testing_REST_APIs.md)).
2. Read-only `JIRA_ISSUE` meta object works in a table/`ReadData`.
3. Selected-ticket AI concept renders bounded ticket fields into agent
   instructions (not full raw Jira JSON).
4. Read-only Jira search AI tool (bounded fields, max results, restricted
   JQL) for broader questions.
5. Only then consider write tools such as the two above, each with its own
   tightly-scoped `allowed_key_prefixes`/`allowed_key_pattern`.
